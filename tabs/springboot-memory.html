힙이 꽉 차고 GC가 계속 도는 상황에서 어떤 인스턴스가 더 싸게 버티는가 | C·M·R 6~9세대 기본형·flex

G1GC · 힙 = RAM 60% · 처리 중 요청이 쌓이며 힙이 차는 운영형 부하 · 서울 리전 On-Demand

목차

무엇을 재현했나

2026-11-05 1차 측정(힙 12GB/24GB 절대값 고정)은 R 패밀리가 RAM의 39%만 힙으로 써 메모리 크기가 비교되지 않아 폐기하고, 힙은 RAM 비율·상주 데이터는 동일 크기로 정해 다시 측정했습니다.

운영에서 메모리 때문에 GC가 도는 전형적인 상황은 이렇습니다. 평소에도 힙의 상당 부분은 캐시·세션 같은 상주 데이터가 차지하고, 트래픽이 몰리거나 하위 시스템(DB·외부 API)이 느려지면 처리 중인 요청이 끝나지 않고 쌓입니다. 요청마다 큰 본문을 받아 객체로 펼쳐 들고 있으므로 쌓인 요청 수만큼 힙이 차고, 결국 GC가 계속 돌며 지연이 폭증하거나 OOM이 납니다.

항목값
상주 데이터전 인스턴스 동일 2GB 캐시(엔트리 4KB). 요청마다 1항목씩 교체(세션·캐시 갱신). 상주 데이터 조건을 같게 두어 인스턴스 간 차이는 처리량이 늘며 쌓이는 작업 객체에서만 나게 했습니다 — 그래야 메모리가 남는데 CPU가 차는지, 메모리가 차서 CPU가 남는지가 인스턴스별로 드러납니다
힙RAM의 60%(-Xms=-Xmx, 실제 값은 표 1). 메모리가 큰 인스턴스는 그만큼 큰 힙을 실제로 씁니다
요청POST /process: 8KB 본문을 1MB 작업 객체로 펼친 뒤 10초 대기(느린 하위 시스템) 후 응답. 대기를 1초로 하면 처리 중 요청 수만큼 초당 요청이 들어와 할당·GC가 CPU를 먼저 포화시켜(스모크에서 r6g가 이론치 절반에서 CPU 93%) "메모리가 꽉 차고 CPU가 남는" 상황이 되지 않습니다. 본문을 작게 둔 것도 네트워크 대역폭이 교란 변수가 되지 않게 하기 위함입니다
부하인스턴스마다 이론 최대 처리 중 요청 수 = (힙 − 상주) ÷ 1MB를 구해, 동시 커넥션을 그 25 → 50 → 60 → 70 → 80 → 90 → 100 → 110%로 늘림(단계마다 90초, 2단계 연속 실패 시 중단). 가상 스레드라 커넥션 수 = 처리 중 요청 수 ≈ 쌓인 작업 객체(1MB씩)
JVMCorretto 21.0.13, Spring Boot 4.1.2, -XX:+UseG1GC -XX:MaxGCPauseMillis=100, 힙 고정(-Xms=-Xmx), AlwaysPreTouch, ExitOnOutOfMemoryError(OOM 시 재시작). 나머지는 JVM 기본값
판정단계 통과 = p99 ≤ 대기 + 1초(11초) + 오류 0 + OOM 재시작 없음. 버틴 커넥션 = 연속으로 통과한 가장 높은 단계(5회 중앙값). GC 정지 비율은 원인 설명용 참고값
배치서버 = 대상 인스턴스 단독 노드(같은 AZ), 클라이언트 = 전용 c6in.2xlarge(wrk)

인스턴스별 결과

표 1. 버틴 동시 커넥션과 비용(5회 중앙값). "1,000커넥션당 비용" = 시간당 가격 ÷ (버틴 커넥션 ÷ 1,000). "가격 대비 성능" = (버틴 커넥션 ÷ m7i.xlarge의 버틴 커넥션) ÷ (시간당 가격 ÷ m7i.xlarge 가격). GC 비율 = 각 인스턴스가 버틴 단계의 90초 중 GC 정지가 차지한 시간(%).
