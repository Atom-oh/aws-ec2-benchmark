힙이 꽉 차고 GC가 계속 도는 상황에서 어떤 인스턴스가 더 싸게 버티는가 | C·M·R 6~9세대 기본형·flex 24개

G1GC · 힙 12GB / 24GB · 처리 중 요청이 쌓이며 힙이 차는 운영형 부하 · 서울 리전 On-Demand

목차

무엇을 재현했나

운영에서 메모리 때문에 GC가 도는 전형적인 상황은 이렇습니다. 평소에도 힙의 상당 부분은 캐시·세션 같은 상주 데이터가 차지하고, 트래픽이 몰리거나 하위 시스템(DB·외부 API)이 느려지면 처리 중인 요청이 끝나지 않고 쌓입니다. 요청마다 큰 본문을 받아 객체로 펼쳐 들고 있으므로 쌓인 요청 수만큼 힙이 차고, 결국 GC가 계속 돌며 지연이 폭증하거나 OOM이 납니다.

항목값
상주 데이터힙의 50%를 캐시(엔트리 4KB)로 채움 — 힙 12GB 단계 6GB, 24GB 단계 12GB. 요청마다 1항목씩 교체(세션·캐시 갱신)
요청POST /process: 64KB 본문을 1MB 작업 객체로 펼친 뒤 1초 대기(느린 하위 시스템) 후 응답
부하동시 커넥션 256 → 1,024 → 2,048 → 3,072 → 4,096 → 6,144, 단계마다 60초. 가상 스레드라 커넥션 수 = 처리 중 요청 수 ≈ 쌓인 작업 객체(1MB씩)
JVMCorretto 21.0.13, Spring Boot 4.1.2, -XX:+UseG1GC -XX:MaxGCPauseMillis=100, 힙 고정(-Xms=-Xmx), AlwaysPreTouch, ExitOnOutOfMemoryError(OOM 시 재시작). 나머지는 JVM 기본값
메모리가 부족한 인스턴스탈락시키지 않고 힙을 RAM − 2.5GB로 줄여 측정(C 패밀리는 힙 약 5.2GB, 상주 데이터 약 2.6GB) — 표에 "축소"로 표시
판정단계 통과 = p99 2초 이하 + 오류 0(사용자 체감 기준). 버틴 커넥션 = 연속으로 통과한 가장 높은 단계(5회 중앙값). GC 정지 비율은 원인 설명용 참고값
배치서버 = 대상 인스턴스 단독 노드(같은 AZ), 클라이언트 = 전용 c6in.2xlarge(wrk)

인스턴스별 결과

표 1. 버틴 동시 커넥션과 비용. "1,000커넥션당 비용" = 시간당 가격 ÷ (버틴 커넥션 ÷ 1,000), 두 힙 단계 중 더 많이 버틴 쪽 기준. GC 비율은 힙 12GB에서 각 인스턴스가 버틴 단계의 60초 중 GC 정지가 차지한 시간(%).

커넥션이 늘 때 지연은 어떻게 무너지나

그림 1. 힙 12GB — 커넥션별 p99(초, 5회 중앙값). 점선 = 판정 기준 2초. 단계에서 OOM·오류가 나면 점이 없습니다.

그림 2. 힙 24GB(R 패밀리) — 커넥션별 p99(초).
