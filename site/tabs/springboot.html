1. 측정 환경과 방법

Karpenter가 인스턴스 타입마다 전용 노드를 프로비저닝하고, podAntiAffinity로 노드마다 벤치마크 Pod를 하나만 배치했습니다. 서버와 부하 발생기는 서로 다른 노드에 두되, podAffinity로 같은 가용 영역에 묶었습니다.

2. 측정 신뢰도

wrk 로그 270개 모두에서 소켓 오류(connect/read/write/timeout)와 HTTP 오류가 0건이라 폐기한 회차는 없습니다. 다만 인스턴스 타입마다 EC2 호스트 한 대에서 측정했기 때문에 호스트 편차는 결과에 그대로 남습니다.

표 4. 회차 간 변동이 큰 인스턴스

같은 설정을 다른 세션에서 다시 쟀을 때

그림 1. 재측정 세션 ÷ 현재 세션 (Graviton, 둘 다 C2 전용). 회색 띠는 ±5%입니다.

결과를 해석할 때 유의할 점

  • 측정 당시 서버/클라이언트 CPU 사용률, 부하 중 클럭, 스레드 덤프는 수집하지 않았습니다. 그래서 부하 발생기가 병목이 아니었다는 직접 증거는 없습니다. 대신 1위 인스턴스가 2위보다 20% 높은 값을 냈으므로 wrk 2스레드의 상한은 그보다 위에 있습니다.
  • 처리량 앱은 고정 문자열 응답 하나입니다. Tomcat 요청 처리와 네트워크 스택 비용이 대부분이라, JSON 직렬화나 DB 접근이 많은 서비스에서는 격차가 달라질 수 있습니다.
  • wrk는 응답을 받은 뒤 다음 요청을 보내는 closed-loop 방식입니다. 최대 처리량 비교에는 맞지만, 목표 요청률에서 SLO를 지키는지는 고정 요청률 도구로 따로 측정해야 합니다.

10. JVM 프로파일의 영향

본 처리량 측정은 아키텍처별 JIT 전략 차이를 배제하려고 Tiered 컴파일을 끄고 C2 컴파일러만 사용했습니다(-XX:-TieredCompilation). 운영 환경에서 주로 쓰는 JVM 기본값(Tiered 켜짐)으로는 2026-01에 6개 인스턴스를 10분 지속 부하(wrk -t2 -c100, 10초 샘플 60개 × 5회)로 측정한 기록이 있어, 같은 커넥션 수(100)끼리 비교했습니다.

그림 7. JVM 기본값 ÷ C2 전용 (커넥션 100). 두 값은 다른 세션이라 ±5% 안팎의 재측정 편차가 섞여 있습니다.
