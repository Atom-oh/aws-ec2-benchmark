48시간 변화

피크와 평상시를 한 선에 그리면 지그재그가 되어 읽기 어려우므로, 같은 종류의 구간만 골라 시간에 따라 이어 봅니다. 기본은 피크 구간의 m7i 대비 배수입니다. 처리량은 높을수록 유리하고, 지연·미발생은 낮을수록 유리합니다. CPU·힙 사용량은 높고 낮음만으로 성능 우열을 판단하지 않습니다. 각 점은 한 구간의 통계이고 점 사이 선은 실제 순간값이 아닙니다. 범례를 눌러 타입을 숨길 수 있고, 점에 마우스를 올리면 구간 이름·목표 RPS·원래 품질 플래그가 나옵니다.

Flex 안정성 상세 분석

평상시 처리 능력은 유지됐지만, 피크 지연과 지속 부하까지 모두 일정했던 것은 아닙니다. m7i-flex는 둘째 날 후반 동일 피크에서 처리량·p99가 악화되지 않았습니다. m8i-flex는 후반 5·15·60분 피크 p99가 전반보다 7.4–11.1% 높았고, 별도 연속 부하에서는 두 Flex 모두 초반보다 낮은 probe 처리량이 오래 유지됐습니다. 재시작 없이 실행됐다는 사실과 지연·손실까지 안정적이었다는 판정은 구분합니다.

같은 피크를 반복했을 때: 24–36시간 → 36–48시간

첫날과 둘째 날은 부하 패턴이 다릅니다. 시간에 따른 변화를 확인하려고 둘째 날 동일한 4시간 주기의 1–3회와 4–6회를 비교했습니다. 각 행은 같은 길이의 90k 목표 피크 3개씩을 합산합니다. RPS는 성공 요청 수 ÷ 시간, p99는 요청 히스토그램 합산값입니다. 아래는 품질 경고가 있는 구간을 포함한 전체 관측이며, 인스턴스 고유 성능에 대한 확정 판정이 아닙니다. 원래 판정 교집합의 기준은 m7i-flex에는 m7i, m8i-flex에는 m8i입니다.

m7i-flex의 후반 처리량은 0.2–3.8% 증가했고, p99는 0.9–3.4% 감소했습니다. m8i-flex 처리량 변화는 −1.4%에서 +1.2%로 작았지만, 15분 피크 p99는 41.471 → 46.079ms, 60분은 41.471 → 45.055ms였습니다. m8i-flex의 높은 m7i 대비 처리량에는 세대 차이가 섞이므로 m8i 표준형을 동시 기준으로도 확인했습니다. 후반 60분 피크에서 m8i-flex ÷ m8i는 처리량 1.013배, p99 1.011배입니다. 피크 전체의 처리량이 비슷해도 tail latency는 별도로 봐야 합니다.

기준선도 변합니다. 같은 60분 피크에서 m7i 표준형은 전반 66,604 → 후반 63,730 RPS(−4.3%)였습니다. 따라서 m7i-flex ÷ m7i가 0.970 → 1.015배로 좋아진 것은 Flex 자체의 큰 성능 향상을 뜻하지 않습니다. 실제 Flex 처리량 변화는 +0.2%였습니다. 시간에 따른 안정성은 상대 배수와 절대 처리량·지연을 함께 확인했습니다.

평균이 가리는 변동: 60분 피크 6회

6회 성공 RPS의 변동계수(표준편차 ÷ 평균)는 m7i-flex 2.49%, m8i-flex 0.50%입니다. 반면 m8i-flex의 4회차 p99는 49.663ms로 높아졌다가 5·6회차 42.495/43.007ms로 낮아졌습니다. 4회차 15분 피크 p99도 53.247ms였습니다. 계속 악화되는 단조 추세와 일시적 지연 증가를 구분해야 합니다. 해당 구간에는 클라이언트 CPU·dispatch 경고가 함께 있어, Flex 제한 또는 GC가 원인이라고 확정하지 않습니다. 6회는 같은 호스트의 연속 관측이며 독립 실험 6회가 아닙니다.

피크 뒤 평상시 처리 능력과 회복의 한계

23,493 RPS 평상시 부하에서 두 Flex의 p99는 전반·후반 모두 같은 히스토그램 값입니다. 이 표는 0도착 boost 휴지 예외 후 대상과 같은 세대 표준형이 모두 통과한 구간만 사용합니다. 통과 구간 구성이 달라 완전히 같은 노출 시간은 아니며, 전체 30개 평상시 구간의 관측에서도 처리량·p99 유지가 확인됩니다. m8i-flex는 같은 세대 m8i보다 p99가 약 2.5% 높습니다. 두 Flex 모두 원래 24개 회복 판정이 무효이므로 몇 초 만에 복귀했는지, 모든 피크 직후 30초 안에 회복했는지는 확정할 수 없습니다. null을 회복 실패 또는 0초 회복으로 해석하지 않습니다.

실행 연속성 · 실패 · 메모리

base/boost는 모두 COMPLETE이며 JVM uptime 재설정·메트릭 수집 오류는 0건입니다. 그러나 timeout은 m7i-flex 2,282건, m8i-flex 4,096건이므로 무오류 실행은 아닙니다. 48시간 전체 미발생 비율과 앞선 피크 전용 비율은 분모가 다릅니다. 미발생 중 동시 요청 한도 원인은 각각 98.7%/81.9%이며, 서버 응답 대기와 클라이언트 제한이 모두 영향을 줄 수 있습니다. 전송된 요청의 작은 오류율만으로 예정 요청 전체를 처리했다고 판단하면 안 됩니다.

둘째 날 평상시 평균 힙은 m7i-flex 1.725 → 1.903GiB, m8i-flex 1.875 → 2.082GiB로 증가했습니다. 이는 10초 Actuator heap-used 표본이며 RSS나 GC 직후 live set이 아닙니다. 이 자료만으로 메모리 누수 유무를 판정하지 않습니다. 최대 GC pause는 위 표의 관측값이고 GC 횟수·정지 합계는 확보 로그의 하한입니다. 로그 보존 추정이 100%여도 원자적 수집·완전 보존을 보증하지 않습니다.

별도 연속 부하: 초반 처리량을 계속 유지했나

이 실험은 지속 wrk 부하와 함께 약 1분마다 수행한 60초 probe입니다. probe RPS는 서버 전체 처리량이 아니며, p99 열은 probe별 p99의 중앙값입니다. 첫 1시간 대비 마지막 30표본에서 m7i-flex RPS는 −18.2%, p99 중앙값은 7.610 → 15.165ms(+99.3%); m8i-flex는 −15.1%, 7.340 → 12.220ms(+66.5%)였습니다. 6시간 이후에는 낮아진 처리량 대역에서 움직이며 확보된 약 47.47시간 동안 계속 감소한 형태는 아닙니다.

저하가 시작된 시점을 기술하기 위해 첫 1시간 평균의 90% 미만인 probe가 5개 연속(인접 간격 ≤90초) 나타나는 첫 묶음을 찾았습니다. 그 첫 표본의 종료 시점은 m7i-flex 약 1.27시간, m8i-flex 약 1.45시간이며 5개 확인 시점은 1.34/1.52시간입니다. 60초 측정창의 종료 시각에 기반한 관측 기준이므로 정확한 내부 제한 시작 시각은 아닙니다. 90%·5표본은 분석용 설정이며 AWS 정책 또는 서비스 SLA 임계값이 아닙니다.

타입별 2,842개 표본의 최대 간격은 61초이고 probe HTTP/소켓 오류는 0건입니다. 하지만 마지막 기록은 각각 47.468/47.462시간으로 끝의 약 32분과 COMPLETE 상태가 없습니다. 관측 probe 사이의 전체 요청 오류·연속 부하 완료를 보증하지 않으며, 48시간 완료 실험으로 합산하지 않습니다.

결론: 실제 운영과 배치에 어디까지 쓸 수 있나

권고는 조건부 운영 도입입니다. 판단 기준은 업무 이름보다 CPU 부하의 지속시간과 지연·완료시간 목표입니다. 아래 권고는 이번 관측과 AWS 성능 설명을 바탕으로 한 운영 판단이며, 실제 API·DB 연동 서비스나 배치 작업을 직접 검증한 결과는 아닙니다.

평균 CPU가 낮고 피크가 간헐적인 웹·API — 후보로 검토할 수 있습니다. 이 정적 응답 앱의 평상시 약 23,493 RPS에서 두 Flex의 처리량과 p99는 둘째 날 전반·후반에 유지됐고 JVM 재시작은 없었습니다. 다만 전체 실행에 timeout은 있었고 피크 직후 회복 시간은 확정하지 못했습니다. 평균 CPU가 낮고 피크 사이에 여유가 있는 서비스라면, 실제 앱의 지연 목표를 확인한 뒤 일부 트래픽부터 도입할 근거가 있습니다. 다만 이 RPS를 DB·인증·외부 호출이 있는 서비스의 수용량으로 가져오면 안 됩니다. 복제본과 자동 확장이 있어도 확장 완료 전의 피크를 감당하는지는 별도 검증해야 합니다.

엄격한 p99 또는 상시 고부하 운영 — 고정 성능 인스턴스를 우선 비교하십시오. m8i-flex의 후반 5·15·60분 피크 p99는 전반보다 7.4–11.1% 높았지만, 같은 후반 60분 피크에서 m8i 대비 처리량 1.013배·p99 1.011배로 표준형과 비슷했습니다. 이번 90k 목표를 미발생 요청 없이 처리한 비교군도 없으므로, 이 관측은 표준형 우위의 근거가 아닙니다. 상시 고부하의 우선 비교 권고는 AWS가 지속적으로 높은 CPU를 쓰는 업무에 고정 성능 인스턴스를 권장한다는 설명에 근거합니다. 엄격한 p99에 대해서는 이번 자료가 서비스 목표 충족을 입증하지 못하므로, CPU 성능의 지속성을 우선 확보하고 실제 앱을 비교 검증하자는 보수적 운영 판단입니다. 낮은 평균 CPU와 엄격한 지연 조건이 겹치면 이 기준을 우선 적용하되, 표준형 선택 자체도 지연 목표 충족을 보장하지 않습니다.

간헐적 비동기·배치 — 완료 기한에 여유가 있을 때 도입 후보입니다. 큐로 유입량을 조절하고, 작업을 분할하거나 재시도할 수 있으며, 처리 속도의 변화를 흡수할 수 있는 업무부터 검토할 수 있습니다. 재시도 시 중복 처리를 막고 큐 대기시간·작업 완료시간까지 확인해야 합니다. 짧은 작업도 연속으로 몰리면 호스트는 지속 고부하가 되므로 개별 작업 길이만으로 적합성을 판단하지 마십시오.

장시간 CPU 집약 배치 — 배치라는 이유만으로 Flex를 우선하지 않습니다. 인코딩·압축·대규모 계산처럼 CPU를 오래 쓰거나 완료 시각이 엄격한 작업은 고정 성능 인스턴스를 우선 비교하는 편이 합리적입니다. 별도 연속 부하에서 마지막 30개 probe의 처리량은 첫 1시간보다 m7i-flex 18.2%, m8i-flex 15.1% 낮았습니다. 이는 지속 용량을 초기 성능으로 잡지 말아야 할 근거이며, 실제 배치 처리량이나 소요시간이 같은 비율로 변한다는 뜻은 아닙니다. 이 보조 실험은 약 47.47시간의 probe 관측이며 표준형 동시 비교군도 없습니다.
